# bhumi Security Audit — 2026-07-02

**Auditor:** Claude Code (under user direction)
**Version audited:** 0.5.1 (M1–M4 complete)
**Cyrius toolchain:** 6.3.34
**Methodology:** adversarial multi-agent code review + code-pattern scan +
property fuzzing + cross-target ABI verification against the agnos kernel source.

## Executive summary

| Severity | Count | Status @ 0.5.1 ship |
|---|---|---|
| CRITICAL | 0 | — |
| HIGH | 0 | — |
| MEDIUM | 1 | **FIXED** (F-1, in 0.5.0) |
| LOW | 0 | — |
| Defense-in-depth | 1 | **DOCUMENTED + MITIGATED** (F-2, opt-in verify hook in 0.5.1) |

**No known security issues ship in 0.5.1.** The single reachable defect (F-1, a
null-capability crash) was found by the pre-release adversarial review and fixed
in 0.5.0 with regression coverage. The design's one trust assumption (F-2, the
lean-enforcer trusting capability issuance) is documented in
[ADR 0002](../adr/0002-seat-lean-capability-enforcer.md) and now carries an opt-in
cryptographic mitigation (`bhumi_cap_verify`). Verification: 200 tests + the
`bhumi.fcyr` fuzz harness clean at 200k iterations; five programs cross-compile
`--agnos` and emit exactly the expected device syscalls.

## Scope

`src/*.cyr` — output.cyr, scanout.cyr, pattern.cyr, input.cyr, kbscan.cyr,
seat.cyr, backend.cyr — plus the `programs/` demos. bhumi is a userland platform
backend: framebuffer scanout (agnos `fbinfo`#38 / `blit`#39), USB-HID keyboard
input (`kbscan`#42), and a capability-gated seat. It performs **no** networking,
filesystem writes, process spawning, or cryptography of its own.

## Threat model

- **Assets:** the framebuffer (screen output) and the keyboard (input stream).
- **Primary threat:** a backgrounded / unauthorized session reading keystrokes or
  scribbling on the screen — the Linux DRM-master / logind problem, solved here
  without uids, logind, or a setuid helper.
- **Defense:** the seat gate — every device op (`bhumi_seat_present` /
  `bhumi_seat_poll`, and the `bhumi_backend_*` facade) requires an **active** seat
  holding a **capability** that grants that device and has not expired. A
  background seat is denied; `BhumiSeatMgr` enforces exactly one active seat.
- **Trust boundary (lean enforcer, ADR 0002):** bhumi *enforces* capabilities and
  *trusts* their issuance to sigil (auth issuer) and kavach (sandbox). Crypto and
  sandbox confinement are explicitly out of bhumi's scope.

## Methodology

### Adversarial multi-agent review

Four independent reviewers (correctness, capability/gate security, cross-target
ABI, memory/resource) swept `src/`, each finding then subjected to an adversarial
verify pass instructed to *refute* it. One finding survived verification (F-1).

### Code-pattern scan

- **Command injection / shell exec** (`sys_system`, `/bin/sh`, `syscall(59)`,
  `sys_execve`): **none** — bhumi never shells out or spawns.
- **Raw `syscall()` sites in `src/`:** **none** — all kernel access goes through
  the audited stdlib wrappers (`sys_fbinfo` / `sys_blit` / `sys_kbscan`), each
  inside a `#ifdef CYRIUS_TARGET_AGNOS` seam.
- **Large in-function stack buffers** (`var buf[N]`, N ≥ 4096 — the Cyrius
  static-data hazard): **none**. The largest are the 64-byte drain buffer and a
  256-byte event buffer; the framebuffer is heap-allocated.
- **Filesystem writes to system paths** (`/etc`, `/bin`, `/sbin`): **none**.

### Property fuzzing

`fuzz/bhumi.fcyr` (`cyrius fuzz`, clean at 200k+ iterations) exercises: framebuffer
bounds round-trips, pixel packing, HID report decode (random 8-byte reports →
bounded, well-formed events), fbinfo accessors, the seat gate (at-most-one-active,
manager consistency, background-always-denied), and the backend gate.

### Cross-target ABI verification

The `fbinfo`#38 (24-byte 6×u32 struct), `blit`#39 (`dstxy` packing, `scale==0`→1),
and `kbscan`#42 (8-byte USB-HID reports) contracts were read verbatim from the
agnos kernel source (`kernel/core/syscall.cyr`). Host stubs return safe sentinels
(-1/0). The `--agnos` builds emit exactly `eax=38/39/42` at the seam call sites
(disassembly-confirmed); `backend-demo` emits all three through one handle.

## Findings

### F-1 — Null-capability dereference in `bhumi_backend_open` — MEDIUM — FIXED (0.5.0)

`bhumi_cap_new` returns 0 on allocator OOM. `bhumi_backend_open(cap, w, h)` passed
`cap` to `bhumi_cap_subject`, which did `load64(cap + 0)` with no guard — a read of
the zero page (crash on agnos userland), and a violation of the function's own
"returns 0 on OOM" contract. Reachable via an OOM-then-open sequence; the
`backend-demo` consumer passed an unchecked `cap`. **Fix:** `if (cap == 0) return 0`
in `bhumi_backend_open` and a `c == 0` guard in `bhumi_cap_subject` (matching its
sibling `bhumi_cap_grants`), with regression tests. Not a privilege issue — a
local crash / DoS on memory exhaustion.

### F-2 — Lean enforcer trusts capability issuance — Defense-in-depth — DOCUMENTED + MITIGATED (0.5.1)

By design (ADR 0002) bhumi does not authenticate a capability's origin; a
capability handed directly to bhumi is honored. This is the deliberate
one-component-one-job boundary — sigil issues, kavach sandboxes, bhumi gates —
and keeps the ~25k-line crypto stack out of the platform layer. **Residual risk:**
a forged capability delivered to bhumi while bypassing sigil/kavach would be
honored. **Mitigation (0.5.1):** the opt-in `bhumi_cap_verify(cap, verify_fn,
pubkey)` hook lets a relying party cryptographically verify provenance over the
cap's authenticated fields via a caller-supplied Ed25519 verifier (e.g. sigil's
`ed25519_verify`) — still with no crypto embedded in bhumi. The default gate
remains possession-based.

## Conclusion

bhumi 0.5.1 ships with **no known CRITICAL or HIGH security issues**. The one
reachable defect is fixed with regression coverage; the sole design trust
assumption is documented and now has an opt-in cryptographic mitigation. The
attack surface is small and well-bounded: no networking, no filesystem writes, no
process spawning, no shelling out, no self-implemented crypto, and every kernel
call is a target-guarded wrapper over a syscall verified against the kernel
source.
